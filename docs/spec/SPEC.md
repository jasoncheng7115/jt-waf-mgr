# jt-waf-mgr 產品規格（草案 v0.1，2026-11-10）

> 本文件可公開。範例網域與位址一律使用 `example.com` 與文件用 IP 區段（RFC 5737）。

## 1. 定位

**jt-waf-mgr** 是 nginx＋libmodsecurity v3＋OWASP CRS 的網頁管理工具。

libmodsecurity v3 沒有官方管理介面：規則、排除、阻擋與開關都是設定檔，調校靠手動編輯與 `nginx -t`。實務上最花時間、也最容易出錯的是：

- 判斷一筆告警是攻擊還是誤判；
- 寫出「最窄」的排除（只對某站台、某路徑、某條規則、某個欄位）；
- 寫出不會誤擋的阻擋規則，並證明它不會擋到正常使用者；
- 改完後確認沒有弄壞站台，壞了能立刻還原。

jt-waf-mgr 把這些步驟做成**有證據、有測試、可還原的變更流程**，並提供 API 讓其他系統（SIEM 管理工具、IPAM、記錄封存）介接。

**不做的事（v1）**：不是 CDN、不做 bot 管理、不做「自動學習後自動放寬」、不取代 CRS 本身、不支援 Apache／Coraza／HAProxy（引擎層留抽象介面，之後再說）。

## 2. 名稱、授權、語言

- 名稱一律小寫 `jt-wazuh-mgr` 式的 **`jt-waf-mgr`**，不翻譯、不放進 i18n 字典。
- 授權 **AGPL-3.0**；介面頁尾要有原始碼連結（AGPL 第 13 條：網路服務要提供原始碼）。
- 介面三語：en（來源語言）、zh-TW、ja。中文用語以台灣用語為準（使用者、記錄、預設、程序…）。
- 文件（README、CHANGELOG、SECURITY）三語。

## 3. 支援環境

- 作業系統：Debian 12／13、Ubuntu 22.04／24.04（x86_64）。
- nginx：nginx.org 套件或發行版套件，1.24 以上；ModSecurity-nginx connector 1.0.x 動態模組。
- libmodsecurity3：3.0.9 以上。
- OWASP CRS：4.x（3.x 只做唯讀顯示）。
- Python：3.11 以上（Debian 12 內建 3.11）。
- **與 nginx 同一台主機**執行（見第 4 節的理由）。
- 必須能**離線安裝**（wheel 與前端建置檔都隨發行檔附上，不從 CDN 載入任何東西）。

## 4. 架構

```
 瀏覽器 ──HTTPS──> nginx（只限內網的管理 vhost，例如 waf.example.com）
                      │ proxy 到 127.0.0.1:<port>（或 unix socket）
                      ▼
               jt-waf-mgr（一般使用者 jtwaf，無 root）
                ├─ Web UI＋REST API（/api/v1）
                ├─ 記錄收集：讀 ModSecurity JSON 稽核記錄、nginx 存取記錄（唯讀）
                ├─ SQLite（/var/lib/jt-waf-mgr）
                ├─ 變更流程：草稿 → 靜態檢查 → 證據 → 沙箱測試 → 核准 → 交給套用程式
                └─ 對外：webhook、syslog 稽核事件、匯出 API
                      │ 只交「變更包」（檔案＋雜湊），不交指令
                      ▼
               jt-waf-mgr-apply（root，單一用途的特權套用程式）
                ├─ 全域鎖
                ├─ 備份目前設定（版本快照）
                ├─ 寫入「受管理」的設定檔
                ├─ nginx -t → reload → 等舊 worker 退場
                ├─ 站台健康檢查（設定的網址清單、預期狀態）
                └─ 任何一步失敗 → 自動還原到快照並回報
```

**為什麼跑在 WAF 主機本機**：只需要寫自己的設定檔和 reload nginx，不必保存任何遠端登入金鑰；工具被攻破的影響範圍也只在這台。多台反向代理的集中管理留到 v2（設計上每台各裝一份，由 API 聚合）。

**權限切分**：
- Web 服務以 `jtwaf` 使用者執行，可讀稽核記錄（`adm` 群組或專屬 ACL），**不能**寫 nginx 設定。
- 套用程式 `jt-waf-mgr-apply` 是唯一的 root 元件，觸發方式擇一：systemd path unit 監看 spool 目錄，或 sudoers 只允許 `/usr/lib/jt-waf-mgr/apply <變更包ID>`（沒有其他參數）。
- 套用程式只接受 spool 目錄中、雜湊與資料庫記錄相符的變更包；**不執行任何來自變更包內容的指令**，只寫入固定路徑的受管理檔案。
- 永不使用 `shell=True`；外部指令一律參數陣列。

## 5. 受管理的設定檔模型

### 5.1 檔案配置

jt-waf-mgr **只寫自己的檔案**，預設：

- `/etc/nginx/modsec/jt-waf-mgr/before-crs.conf`：在 CRS 規則之前載入（排除、阻擋、不檢查密碼欄位、外掛啟用）。
- `/etc/nginx/modsec/jt-waf-mgr/after-crs.conf`：在 CRS 規則之後載入（設定期指令如 `SecRuleUpdateTargetById`，以及「超過門檻就擋」與保底拒絕）。
- `/etc/nginx/modsec/jt-waf-mgr/ip-blocks.txt`：暫時封鎖的 IP 清單（`@ipMatchFromFile`）。
- 檔頭寫明「由 jt-waf-mgr 產生，請勿手動編輯」，並記錄產生時間、版本號與內容雜湊。

主設定（例如 `main.conf`）裡的 `Include` 由「導入」步驟加入一次（顯示差異、備份、`nginx -t`，使用者確認後才寫）。之後工具不再碰主設定。

### 5.2 手動修改偵測

- 每次寫入記下雜湊；下次要寫之前比對，不一致就**拒絕覆蓋**，在介面顯示差異，讓使用者選「採用手動版本（匯入）」或「放棄手動修改」。
- 不在受管理檔案裡的規則（例如站台既有的手寫檔）以唯讀方式列出，標示「未受管理」。

### 5.3 規則種類（結構化樣板）

規則一律由樣板產生，使用者填欄位，不直接寫 SecRule（專家模式除外）。

1. **排除（exclusion）**：讓 CRS 在某範圍內不檢查某些東西。欄位：
   - 範圍：Host（完全比對或正則，預設完全比對）、路徑（完全、前綴、正則）、方法（選填）、來源（全部／只內網／只外部，選填）；
   - 動作：`ruleRemoveTargetById`（某規則不看某欄位，**預設且推薦**）、`ruleRemoveById`（整條規則不做）、`ruleRemoveByTag`（整類，要特別確認）、「只計分不阻擋」（移除超過門檻阻擋的那條）；
   - 規則 ID 或 tag、目標變數（`ARGS:xxx`、`REQUEST_BODY` 等）。
2. **確定阻擋（confident block）**：只對外部來源生效的明確特徵。欄位：
   - 比對目標：路徑（`REQUEST_FILENAME`，預設經 `t:urlDecodeUni,t:normalizePath,t:lowercase`）、完整網址、User-Agent、Host、指定標頭；
   - 正則；
   - 固定的例外清單（例如 WebDAV、分享連結路徑，站台可設定）；
   - 說明、參考（CVE、公告網址）、依據（證據數字，自動帶入）。
   - 產生的規則形式固定：命中且來源不在內網清單 → `setvar:tx.<flag>=1,ctl:ruleEngine=On`，並由「加分讓 949110 決定」與「保底拒絕」兩條系統規則處理（見 5.5）。
3. **不檢查敏感欄位（redaction / no-inspect）**：密碼等欄位不被規則比對，避免明文進稽核記錄。預設清單：`password`、`passwd`、`pass`、`pwd`、`secret`、`token`、`otp`、`credential`、`client_secret`…（可設定）；可限定 Host＋路徑（例如 RPC 介面把密碼放在位置參數）。
4. **外掛啟用（plugin toggle）**：CRS 外掛（WordPress、Nextcloud…）預設關，依 Host 開。
5. **專家模式（raw）**：直接貼 SecRule。只限管理者；一律要求測試案例；靜態檢查禁止全域關引擎、`exec`、修改稽核設定等危險動作（清單見 5.6）。從既有設定匯入的規則先以這種形式保存，原文不變。

### 5.4 規則 ID 配置

- ID 範圍可設定，預設：
  - 系統規則 10000–10099（外掛預設關、方法、站台理解類）；
  - 排除 10100–10199；
  - 確定阻擋 10200–10296；
  - 系統保留 10297–10299（超過門檻就擋、加分、保底拒絕）。
- **ID 永不重複使用**：停用或刪除的規則 ID 保留在資料庫（墓碑），新規則一律往後配。
- 啟動與導入時掃描 `nginx -T` 的完整設定，**任何已被其他檔案使用的 ID 都視為已占用**（包含 vhost 內 `modsecurity_rules` 的內嵌規則）。

### 5.5 系統規則（工具內建、不可刪）

- **只計分不擋的全域模式**：引擎全域 `DetectionOnly`，個別請求在命中確定阻擋時以 `ctl:ruleEngine=On` 打開。
- **外部超過 CRS 門檻就擋**（可關）：CRS 的 949110 跑完後，外部來源分數 ≥ 門檻就打開引擎並交給保底拒絕。
- **加分讓 949110 決定**：確定阻擋命中時加一個 critical 分數，讓 CRS 自己的 949110 做出阻擋決定（SIEM 端以 949110 判斷「已阻擋」）。
- **保底拒絕**：若分數仍不足門檻（例如有排除移除了分數），旗標為 1 就 403。
- 「內網」位址清單是**一個設定值**，由工具展開到所有用到的規則（不要在每條規則各寫一份）。

### 5.6 靜態檢查（每個變更都要過）

- 樣板欄位驗證：Host、路徑格式；正則可用 PCRE2 編譯；禁止空正則、`.*` 開頭結尾全包、只有萬用字元的樣式。
- ReDoS 防護：巢狀量詞、交替內重複量詞等形狀直接拒絕；另以實際的 `SecPcreMatchLimit` 跑一組長字串測試。
- ID 不衝突、在範圍內。
- 專家模式禁止：`SecRuleEngine Off`、全域 `ctl:ruleEngine=Off`、`exec:`、`SecAuditEngine` 等稽核設定、`SecRequestBodyAccess Off`、`SecRuleRemoveById` 移除系統規則、`setenv`。
- 產生後整份設定以沙箱 nginx 做 `nginx -t`（見 6.3）。

## 6. 變更流程（核心）

```
 草稿 ─> 靜態檢查 ─> 證據檢查 ─> 沙箱測試 ─> 核准 ─> 套用 ─> 上線後檢查 ─> 完成
                 │失敗          │不符條件      │失敗       │拒絕     │失敗           │失敗
                 └────────────── 退回草稿並說明原因 ─────────┘         └─> 自動還原 ─┘
```

### 6.1 方向分類

每個變更自動分類為**收緊**（新增確定阻擋、暫時封鎖 IP、重新啟用規則）或**放寬**（新增排除、停用規則、移除封鎖、降低門檻）。

- **放寬一律要有核准者按同意**，不論誰提出、不論是否通過所有檢查。
- 收緊可設定成「通過所有檢查後自動套用」（預設關，由管理者開啟），否則同樣要核准。
- 透過 API 提出的變更**永遠不能自己核准**（見 API.md）。

### 6.2 證據檢查（evidence）

對確定阻擋，從 nginx 存取記錄與稽核記錄的索引計算：

- 外部來源命中次數、其中拿到 2xx／3xx 的次數（排除「任何路徑都回同一頁」的站台，可設定）；
- 內網來源命中次數（排除設定的已知掃描器與測試主機）；
- 依站台、依來源的分布與樣本。

預設通過條件：外部 2xx／3xx＝0 且內網命中＝0；不符時列出樣本，由使用者判斷（可附理由強制送出，但會被記錄並必須核准）。

對排除，計算「這個排除會讓哪些過去的告警消失」，並標出其中**來自外部且看起來像攻擊**的筆數（避免排除寫太寬）。

存取記錄的索引：每天彙總（站台、路徑形狀、狀態碼、來源類型、UA 類型）存在 SQLite，原始記錄不複製；保留天數可設定。支援 nginx `combined` 與 JSON 格式（欄位對照可設定）。

### 6.3 沙箱測試

- 在本機以臨時 nginx（只聽 127.0.0.1 的隨機埠）載入**正式的完整 ModSecurity 設定＋這次的變更**，後端接一個固定回 200 的假服務；稽核記錄寫到臨時目錄，**不進正式記錄、不送 SIEM**。
- 用 `X-Forwarded-For` 模擬外部與內網來源（只在沙箱信任；正式設定永遠不信任用戶端標頭）。
- 測試案例：
  - 使用者為這個變更寫的案例（預期狀態碼、內外部、Host、路徑、UA、標頭、本體）；
  - **固定回歸案例**：每個站台的「正常請求樣本」（由存取記錄自動抽樣 2xx 的路徑形狀，加上使用者標記的重要網址）——收緊類變更不得讓任何一個變成 403；
  - 放寬類：造成告警的那筆請求（重放）現在應該不再被擋／不再告警，同類攻擊樣本仍要被擋。
- 每筆 403 都要確認是由預期的規則決定（例如 949110 而不是保底），結果寫入變更記錄。
- 沙箱結束一律清除程序與暫存檔，並確認沒有殘留監聽埠。

### 6.4 套用與還原

- 由套用程式執行：取得鎖 → 快照（受管理檔案＋主設定的雜湊）→ 寫入 → `nginx -t` → `nginx -s reload`（或 `systemctl reload`）→ 等舊 worker 退場（預設最多 120 秒）→ 站台健康檢查 → 完成。
- 健康檢查：設定的網址清單（Host、路徑、預期狀態碼或狀態碼類別、內容長度範圍選填），套用前後各跑一次比較，有差異即還原。
- 還原：一鍵回到任何一個歷史版本（同樣經過 `nginx -t`、reload、健康檢查）。
- **nginx 動態模組與 nginx 版本綁定**：reload 前檢查 `nginx -V` 與模組編譯版本是否一致，不一致時拒絕並警告（reload 可能靜靜失敗、繼續跑舊設定）。

### 6.5 稽核

每個動作（登入、提出、核准、拒絕、套用、還原、設定變更、API token 使用）都記錄在資料庫，並以一行 JSON 寫到 syslog（facility 可設定，program name `jt-waf-mgr`），讓 SIEM 收集。寫入前跳脫換行與控制字元（防止記錄注入）。

## 7. 介面

1. **總覽**：24 小時／7 天的被擋、只記錄、依站台、依來源、依規則類別；**「只靠 CRS 分數擋下」**清單（最可能的誤擋）置頂；可設定「重點關注站台」（例如 SSO），每個重點站台一張卡片。
2. **事件**：依時間、站台、路徑、來源、規則、結果篩選；詳細頁顯示請求行、命中的規則與命中內容（已遮蔽敏感欄位）、相關的存取記錄；動作按鈕：「為這筆建立排除」「建立類似的阻擋」「查這個 IP」（介接 IPAM）。
3. **規則**：受管理規則清單（類型、範圍、說明、依據、建立者、建立時間、7／30 天命中數、最後命中），啟用、停用、編輯、複製、測試；未受管理的規則唯讀顯示。
4. **變更**：草稿、待核准、歷史；每筆顯示差異、證據、沙箱結果、核准紀錄；還原按鈕。
5. **站台**：從 `nginx -T` 解析出的 server 區塊清單——是否啟用 WAF、阻擋模式、不經 WAF 的 location（`modsecurity off`）、本體上限、是否只限內網或國家；v1 唯讀。
6. **CRS**：版本、偏執等級、門檻、外掛、更新狀態（只檢查並通知；更新本身可由外部腳本或後續版本處理）。
7. **定期報告**：排程產生「這段時間發生了什麼」的摘要（新特徵、被擋清單、只靠分數擋下的清單、候選阻擋），以 webhook／email 送出。
8. **設定**：內網位址、ID 範圍、健康檢查網址、已知掃描器、敏感欄位清單、整合（IPAM、webhook）、API token、使用者與角色。

**顯示攻擊者控制的內容**：網址、UA、標頭、本體都是攻擊者寫的，前端**一律以文字節點顯示**（禁止 `innerHTML`），長字串截斷，不可見字元標示出來；有專門的測試餵入 XSS 與終端機跳脫序列的事件。

## 8. 認證與權限

- 人：OIDC（Keycloak 或任何相容的 IdP），必要時可要求 IdP 端的雙因素驗證（檢查 `amr`／`acr`）。
- 角色：
  - `viewer`：看；
  - `operator`：提出變更、套用已核准的收緊；
  - `approver`：核准或拒絕（含放寬）；
  - `admin`：設定、token、角色。
  - 同一筆變更的提出者不能是核准者（可在單人環境由管理者明確關閉這條，並記錄）。
- 緊急本機帳號：預設停用，啟用需 TOTP，只能從本機或指定網段登入。
- API：見 API.md（scope 型 token）。
- Session cookie：HTTPS 一律 `__Host-` 前綴＋Secure＋HttpOnly＋SameSite=Lax；CSRF token；閒置逾時。

## 9. 安全需求

- 符合 OWASP Top 10 2025；每次發版跑 OWASP ZAP，並與基準逐項比對（以 plugin ID 比對）。
- **CSP 從第一天就不允許 `unsafe-inline`**（前端是獨立的靜態檔，不內嵌在程式字串裡）。
- 服務只聽 127.0.0.1 或 unix socket；管理 vhost 由 nginx 限定內網，並建議再限定管理網段。
- 敏感欄位遮蔽：事件寫入資料庫前就遮蔽；匯出與 API 回應同樣遮蔽。
- 記錄注入：所有寫到 syslog、webhook、報告的內容都跳脫換行與控制字元。
- 稽核記錄的讀取只用串流解析，單筆大小上限（例如 1 MB），解析失敗計數但不中斷。
- 相依套件鎖版本、附離線 wheel；發版前掃描已知弱點。
- 發行內容不得包含任何特定站台的主機名、IP、郵件帳號（以 preflight 檢查擋住）。

## 10. 資料保存

- SQLite（WAL），預設 `/var/lib/jt-waf-mgr/jt-waf-mgr.db`。
- 事件：預設保留 30 天（可設定）；彙總統計保留 1 年；變更與稽核紀錄永久保留。
- 匯出：NDJSON（gzip）＋SHA-256，供記錄封存系統取走（見 API.md）。
- 設定快照：每次套用一份，預設保留 200 份。

## 11. 安裝與封裝

- `install.sh` 一行安裝＋`--offline`；建立使用者、目錄、systemd 單元（`jt-waf-mgr.service`、套用程式的 path／service 單元）、範例設定 `/etc/jt-waf-mgr/config.yaml`。
- 安裝**不改 nginx 設定**；「導入」是安裝後在介面上做的明確步驟（顯示要改的內容、備份、`nginx -t`、確認後寫入）。
- `uninstall.sh`：移除服務與程式，保留資料與設定快照；受管理的 nginx 設定檔要使用者確認後才移除（並先還原 Include）。

## 12. 測試

- 單元測試完全離線（不需要 nginx）。
- 引擎整合測試：容器（nginx＋libmodsecurity3＋CRS）跑產生的設定與沙箱流程。下載映像前要先取得使用者同意（說明名稱、來源、大小）。
- 「決策等價」測試：導入既有設定時，以歷史請求樣本在導入前後的沙箱各跑一次，允許／拒絕結果必須完全相同。
- 瀏覽器 E2E（headless Chrome）：主要流程、三語、權限、XSS 事件顯示。
- 安全掃描：ZAP（每次發版）。

## 13. 分期

- **P0 基礎**：repo、CLAUDE.md、授權、封裝骨架、設定載入、OIDC 登入、角色、稽核、測試框架、preflight（隱私與版本一致性檢查）。
- **P1 唯讀**：稽核記錄與存取記錄收集、總覽、事件、規則清單（解析既有設定，唯讀）、站台清單、CRS 狀態、唯讀 API（status、events、rules、vhosts、export、lookups）。**可在正式機唯讀試跑。**
- **P2 變更流程**：受管理檔案與導入、樣板（排除、確定阻擋、敏感欄位、外掛）、靜態檢查、證據、沙箱、核准、套用程式、健康檢查、還原、決策等價測試。
- **P3 介接**：暫時封鎖 IP、變更提案 API、webhook、IPAM 名稱補充、SIEM 稽核事件格式定案、匯出給封存系統。
- **P4 營運**：定期報告、重點站台監看、CRS 更新狀態整合、站台阻擋模式切換（vhost 層的編輯，風險最高，最後做）。

每一期結束都要：測試全過、ZAP 無新項目、文件三語、CHANGELOG、tag。
