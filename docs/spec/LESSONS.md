# libmodsecurity v3＋nginx＋CRS 4 的實戰教訓

> 本文件可公開。整理自一個實際站台從 2026-10-31 起的營運紀錄（約 40 個 vhost、每天數十萬請求、每 3 小時一輪檢討）。
> 每一條後面標示「→ 設計要求」：jt-waf-mgr 必須照做或必須偵測。

## 引擎與載入

1. **規則要在 http 層載入一次，vhost 只寫 `modsecurity on;`。** 每個 vhost 各自 `modsecurity_rules_file` 會讓 CRS 編譯 N 次（實測 master 程序 1.2 GB）。→ 導入時偵測並警告「每個 vhost 各載一次」的寫法。
2. **vhost 內嵌的 `modsecurity_rules` 比 http 層同一個 phase 的規則先執行。** 想在 vhost 層改 CRS 設定（例如門檻），在 phase 1 用 `setvar` 會被 `crs-setup.conf` 的初始化蓋掉，要放在 phase 3。→ 站台層覆寫一律產生 phase 3 的 SecAction，並有測試。
3. **動態模組綁死 nginx 版本。** nginx 套件升級後，執行中的仍是舊程式；下一次 reload 載入不相容的模組會靜靜失敗，繼續跑舊設定，看起來「改了但沒生效」。→ 套用前比對 `nginx -V` 與模組；建議 `apt-mark hold` nginx 與模組並在介面顯示。
4. **reload 後舊 worker 會用舊規則再服務一陣子**（實測 1–2 分鐘，長連線更久）。→ 套用後等舊 worker 退場才做健康檢查與「已生效」判定。
5. **libmodsecurity 在 reload 或 USR1 時不會重開稽核記錄檔。** 輪替要用 `copytruncate`，否則記錄寫進已被刪除的檔案。→ 收集程式要處理 inode 變更與截斷；安裝時檢查 logrotate 設定。
6. **大檔上傳必須繞過 WAF。** 模組會把整個請求本體讀進 worker 記憶體（實測 200 MB 上傳讓 worker 多 383 MB）。WebDAV、同步用戶端、線上文件編輯（WOPI）這類路徑要 `location … { modsecurity off; }`，並把 `SecRequestBodyLimit` 設在合理值。→ 站台清單要顯示這些繞過的路徑；新增規則時提醒「這條對繞過路徑無效」。
7. **DetectionOnly 時，connector 寫進 nginx error log 的是 info 等級**，多數 SIEM 收不到。→ 一律從 JSON 稽核記錄收集，不依賴 error log。

## 判斷與規則撰寫

8. **CRS 的 OS 檔案清單含 `.tools/`、`.claude` 等字串**（930120）。網域本身就是 `.tools` 的站台、OIDC 的 `redirect_uri`／`iss` 參數會整天命中。→ 誤判多半是「站台自己的網址出現在參數裡」，排除樣板要能「對某 Host＋某參數名稱移除 930120」。
9. **參數名稱也會被比對**，不只參數值（例如 AI 工具在 JSON 參數名稱裡帶 `claudecode/…`）。→ 排除樣板支援 `ARGS_NAMES:` 目標。
10. **同一段內文會被不同規則以不同變數讀到**：排除 `ARGS:content` 後，944 系列（Java）、921110 等規則仍然讀整個 `REQUEST_BODY`。→ 排除精靈要列出「這個請求裡命中的所有規則與變數」，一次處理完；沙箱重放確認告警真的消失。
11. **用戶端的 Content-Type 與實際本體格式不一致**（例如 SOAP 介面宣稱 `application/soap+xml` 卻送 JSON），XML 解析器失敗（200002）。→ 提供「依 Host＋路徑指定本體解析器（JSON／XML／URLENCODED／不解析）」的樣板。
12. **GET 帶本體**（920170）的正常用戶端存在（輪詢 API 的伺服器端程式）。→ 常見誤判類型要有說明文字，引導使用者用最窄排除。
13. **寫入內容的端點（存草稿、寄信、聊天訊息）本體就是使用者打的字**，帶程式碼、路徑、指令是正常的。外部使用者會因為信件內文被「超過門檻就擋」誤擋。→ 提供「只計分不封鎖」的排除（保留記錄與確定封鎖，只移除分數封鎖）。
14. **路徑類規則要 `t:urlDecodeUni,t:normalizePath,t:lowercase`**，才擋得住 `%6d`、`//`、`./`、大小寫的繞過；但也要測不會誤殺相似的正常路徑（`/alfabet.php` 不是 `.alfa` web shell）。→ 樣板預設帶這些轉換，沙箱案例自動加入「編碼、大小寫、多斜線」的變體。
15. **檔案路徑類的封鎖要排除 WebDAV 與分享連結路徑**：同步用戶端合法地存取使用者自己的 `.env`、`.git/config`、`CLAUDE.md`。→ 例外清單是每個站台可設定的固定欄位。
16. **確定封鎖只對外部生效**；內網來源（監控、開發、備份、掃描器）只記錄。全域維持 DetectionOnly，命中時以 `ctl:ruleEngine=On` 打開單一請求。→ 系統規則（SPEC 5.5）。
17. **「超過門檻就擋」用 nolog**，所以它決定的封鎖在記錄裡只看得到保底拒絕的那條 ID。→ 事件的 `decided_by` 欄位要由工具推算（有確定封鎖命中＝confident，否則＝score），不要只看記錄裡有哪些 ID。
18. **判斷內網位址要用正式的位址函式庫**，不要用字串前綴（`172.2` 會吃到公網 172.200–255）。→ 單元測試涵蓋邊界。
19. **「網站對任何路徑都回首頁 200 或轉址 301」的站台**會讓「攻擊拿到 2xx/3xx」的統計失真。→ 證據檢查允許標記這類站台，或比對回應大小與首頁相同。
20. **維護頁（503 時的靜態頁）回 200** 也會讓統計失真。→ 同上，可設定「維護頁的大小或路徑」。

## 機密與記錄

21. **ModSecurity v3 沒有 `sanitise*` 動作**：規則一命中，比對到的文字（可能是密碼）就寫進稽核記錄。曾經有 RPC 介面的密碼因此進到記錄。→ 敏感欄位「不檢查」規則是預設安裝內容；收集時再遮蔽一次；介面與 API 沒有看原文的選項。
22. **稽核記錄裡的網址、UA、標頭都是攻擊者寫的**：XSS、終端機跳脫序列、超長字串、換行（記錄注入）。→ 前端只用文字節點；寫到 syslog／webhook 前跳脫換行；有專門的測試資料。
23. **不要信任用戶端的 `X-Forwarded-For`**。經 CDN 的站台用 real-ip 模組以 CDN 位址清單還原；後端應用若開了「proxy 模式」，一定要讓應用只接受代理的連線（否則直連者可偽造來源）。沙箱為了模擬來源才信任 XFF，那個設定絕不能出現在正式設定。→ 站台清單顯示每個站台的 real-ip 設定；沙箱設定與正式設定分開產生。
24. **SIEM 端判斷「已封鎖」的依據要穩定**：讓確定封鎖加 critical 分數，由 CRS 自己的 949110 做決定，SIEM 規則看 949110＋引擎狀態即可。→ 系統規則（SPEC 5.5），改這個行為要同步通知 SIEM 端。

## 流程

25. **每一個封鎖都要先查全部歷史記錄**：外部成功次數、內網命中次數都要是 0（或只有明顯的攻擊）。這一步擋掉了大部分「看起來很合理但會誤擋」的候選。→ 證據檢查是流程中的強制步驟。
26. **測試 nginx 一定要用正式的完整設定**，不是只載新規則；否則測不到與既有排除、CRS 的交互作用。→ 沙箱設計（SPEC 6.3）。
27. **改完一定要讀回結果**（實際請求的狀態碼、規則是否生效），不要只看指令有沒有報錯。→ 套用後健康檢查與「上線後實測」步驟。
28. **規則 ID 被系統片段占用過**（例如 vhost 片段裡的 SecAction 用了 10100），新規則撞號時 `nginx -t` 失敗。→ ID 配置要掃描整個 `nginx -T`，並保留墓碑。
29. **同一時間只能有一方改設定**。人工手改與工具同時改會互相覆蓋。→ 全域鎖＋手動修改偵測。
30. **放寬比收緊危險**。被擋的使用者會抱怨（容易發現）；被放寬的攻擊不會有人抱怨（不會被發現）。→ 放寬一律要人核准，且稽核等級較高。
